# 调研与产品取舍

调研日期：2026-10-08。来源为项目官方仓库、文档、论文作者页面与公开问题记录。Star 为当日 GitHub 页面显示的近似值，仅作社区规模线索，不是质量评分；本表不是性能跑分，也不代表安装测试过所有项目。

## 比较矩阵

| 项目 / 一手来源 | 约 Star | 主要价值 | 对本项目的启发与取舍 |
|---|---:|---|---|
| [COLMAP](https://github.com/colmap/colmap) | 12.9k | 通用 SfM/MVS，已有 GUI、CLI 与自动流程 | 作为成熟几何基线及可选后端；使用其文本交换格式，不宣称首次实现一键重建 |
| [Meshroom](https://github.com/alicevision/Meshroom) | 13.0k | 节点式可视流程与可扩展工具箱 | 节点图适合专业流程；本项目选择少数明确动作，不复制节点 UI |
| [OpenMVG](https://github.com/openMVG/openMVG) | 6.6k | 多视图几何与 SfM 开发库 | 模块边界值得借鉴；不拷贝求解器或在 Python 中伪造同等成熟度 |
| [OpenMVS](https://github.com/cdcseacave/openMVS) | 4.1k | 稠密点、网格与纹理化 | 稀疏结果和稠密表面应分开；不把其 AGPL 源码混入 MIT 核心 |
| [Open3D](https://github.com/isl-org/Open3D) | 14.0k | 点云、配准、RGB-D 与三维处理工具 | 互操作优先；初版避免增加依赖重量，导出标准点云而非私有格式 |
| [WebODM](https://github.com/WebODM/WebODM) | 4.2k | 面向航空影像的项目、地图与三维交付 | 说明任务管理和交付同样重要；本项目不做地理配准、正射影像或航测产品 |
| [Nerfstudio](https://github.com/nerfstudio-project/nerfstudio) | 12.0k | 神经场景表示、渲染与实验工作流 | 新视角渲染不是自动获得可靠封闭几何；本项目优先 CPU、显式相机与可检查误差 |
| [VGGT](https://github.com/facebookresearch/vggt) | 14.5k | 从多视图直接预测相机和几何 | 适合后续受控适配探索，但代码和不同权重条款不同，不默认捆绑 |
| [DUSt3R](https://github.com/naver/dust3r) | 未记录 | 直接恢复点图与几何对齐 | 代码采用 CC BY-NC-SA 4.0，检查点还有数据来源条件；不加入本版默认依赖 |

### 需要避免的过时认识

COLMAP 本身已能运行 CPU 稀疏重建，并不是整个工具都要求 CUDA；其稠密流程有不同硬件要求，见 [FAQ](https://colmap.github.io/faq.html)。ReconTrail 的优势目标不是“发明 CPU 重建”，而是把轻量输入检查、明确的结果边界和离线证据放在同一条小型工作流中。

WebODM 官方仓库当前位于 `WebODM/WebODM`；官方说明其 2026 年已发展为独立项目，并支持不同引擎。不应沿用“只能配合 ODM、只能复杂部署”的旧比较。这里借鉴任务与交付模式，不复制服务端架构。

VGGT 官方 README 区分代码许可、原有非商业检查点与需遵循申请/条款的新商业检查点。不能简单标为“全部可商用”或“全部非商业”。本项目没有下载这些权重。本文是依赖选择记录，不代替对未来新增模型或二进制包的逐项许可审核。

## 需求判断：必要的不是再增加一个黑箱

对小规模采集而言，“是否拍够了、哪组照片断开、结果是什么尺度、能不能交给别人检查”是几何计算前后的实际问题。这是从现有工具职责分布、官方限制和使用问题中形成的产品判断，不是市场份额或用户调研的统计结论。

[Meshroom 的小物体采集问题](https://github.com/alicevision/Meshroom/issues/2591)与 [Nerfstudio 安装问题](https://github.com/nerfstudio-project/nerfstudio/issues/3274)可用作失败路径的个案，不能推导失败率。COLMAP 官方 FAQ 对焦距、纹理、基线、硬件和内存限制的说明，则直接支持在运行前提供采集检查与在结果中保留误差证据。

由此选择四个验收目标：普通电脑能跑一个小示例；不会把诊断分数冒充成功概率；失败有报告而不是只留下异常；几何能导出标准格式并追溯输入与参数。

## 已实施的工程取舍

**CPU 优先，但不重写基础算法。** 使用 OpenCV 的 SIFT/FLANN、五点几何、RANSAC、PnP、三角化和 SGBM，SciPy 的稀疏最小二乘。项目自写输入策略、增量编排、观测管理、几何过滤、优化残差、状态管理、报告及导出。另提供受版本约束的 PyCOLMAP 适配入口。所有基础方法明确归属上游。

**保守输入处理。** 完全一致的解码像素可去重；低清晰度、过曝、欠曝、纹理少只提示，不据此自动删除照片。图连通性来自相对几何验证，不只是外观相似度。小集合枚举配对；大集合用顺序邻域与颜色直方图候选，复杂无序集合可切换全配对，但代价为平方级候选数。

**区分稀疏、稠密与可交付资产。** 默认照片模式只承诺稀疏几何。标定双目提供真实的稠密视差与开放表面，不把点云连线包装为通用封闭网格。未知焦距和未知尺度在报告中显式提示。

**标准输出而非封闭工程格式。** PLY、OBJ、COLMAP 文本、JSON、单文件 HTML。COLMAP 输出包含对应标准化图片和双向轨迹，避免只输出相机却无法继续处理。原始图片不修改；标准化导出不保留 EXIF。

**可维护，而非功能堆叠。** 本地浏览器单用户、单工作进程；任务状态显式持久化；输入和产物分别做哈希校验；恢复只复用完成结果，不虚构中间优化断点。可选后端的验证状态与默认后端分开记录。

## 暂不做什么

暂不提供公网多租户服务、航测坐标、闭合纹理网格、鱼眼全模型、移动端原生应用、神经权重下载、自动尺度恢复和任意视频的准确时间同步。后续优先级应由真实采集失败记录驱动，而不是继续增加未经验证的后端。

推荐下一轮维护首先建立有明确许可的真实场景基准集，并记录注册率、三维表面误差、峰值内存、总耗时及失败样例；只有在同一数据、硬件、参数与质量口径下才比较后端。现有合成测试证明程序链路与部分几何约束，不证明真实数据泛化效果。
